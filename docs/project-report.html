Telepathology Console

A web platform for remote FNAC whole-slide review, annotation and reporting between community health centres and pathologists

Project duration15 June 2026 – 4 September 2026
Repositorygithub.com/GauravKadam30/PAATHOLOGYUI
Scale~7,700 lines across 4 workspaces; 24 REST endpoints; 7 database tables; 23 automated tests

1. Problem

A Community Health Centre can take a fine-needle aspiration sample and prepare a slide, but it rarely has a pathologist on site. The slide must physically travel to one, which takes days, risks breakage, and delays the start of treatment. For tuberculosis diagnosis, where FNAC is heavily used, that delay is clinically significant.

Digitising the slide is only half an answer. A scanner produces images of a size that ordinary web tooling cannot handle: the slide used throughout this project is 135,438 × 57,665 pixels — 7.8 billion pixels, 1.24 GB on disk. No browser can decode that, and no rural connection can download it. Any workable system has to solve the image problem before it can solve the workflow problem.

2. What was built

A three-part system covering the whole consultation, from sample to prescription.

ComponentWho uses itWhat it does
CHC Intake portal Lab attendant Registers a patient and uploads the slide — either an ordinary photograph or a gigapixel scanner file.
Pathology Console Pathologist Live worklist, deep-zoom slide viewer with a micron scale bar and magnification presets, annotation tools, and microscopic findings.
Physician view Physician Reads the findings and annotated slide, records a prescription, and signs the report, which closes the case.

All three are served by one Express API over PostgreSQL, so every participant sees the same record rather than exchanging files.

3. Technical approach

3.1 Serving gigapixel images

The viewer never receives the slide. A Python service backed by OpenSlide reads small Deep Zoom tiles out of the file on demand, and OpenSeadragon requests only the tiles covering the current view. Panning and zooming fetch a few kilobytes each.

The alternative — pre-generating the full tile pyramid when a slide is uploaded — was implemented and measured first, then rejected:

ApproachPreparationExtra storageTile latency
Pre-generated pyramid~20 minutes2.2 GB per slide~1 ms
On demand (adopted)nonenone~20 ms

Twenty milliseconds is imperceptible while panning, so the on-demand design trades a latency nobody notices for twenty minutes and 2.2 GB that everybody pays. The service holds a small LRU cache of open slide handles, because opening a gigabyte file is the expensive part, not reading from one.

Why a separate Python process. OpenSlide is a native C library with no JavaScript equivalent. Rather than compromise on format support, the API starts Python as a supervised child process — restarted automatically with exponential backoff if it dies — and proxies tile requests to it, so the browser only ever talks to one origin.

3.2 Annotations that stay anchored

Marks are stored in image coordinates and re-projected onto the screen every frame, so a circle drawn around a cluster of cells stays on those cells through any amount of zooming and panning.

They are also stored as vector data rather than as a flattened picture. An earlier design composited the slide and the drawing into a PNG: about 16 MB per case, and permanently uneditable. The same two shapes as vectors are roughly 1.2 KB, and remain editable after reloading.

3.3 Clinical correctness

  • A micron scale bar and 4×/10×/20×/40× magnification presets derived from the scanner's own calibration. Where a slide carries no calibration, no scale is shown at all — an invented measurement on a diagnostic image is worse than none.
  • One row per note, per case and per kind. An earlier design stored every patient's notes as a single document, so two clinicians saving at the same moment silently destroyed one of the two sets of notes.
  • Archive instead of delete. A mistaken removal is recoverable; clinical records are rarely safe to destroy.

4. Security and access control

Three roles map onto the three people in a consultation, and the split is enforced on the server rather than merely hidden in the interface:

ActionLab attendantPathologistPhysician
Submit a patient and slideyes——
Annotate a slide—yes—
Write microscopic findings—yesread only
Write the prescription—read onlyyes
Sign and submit the report——yes

Separating pathologist from physician is not bookkeeping. One account writing both the microscopic findings and the prescription removes the second opinion the workflow exists to provide, and leaves an audit unable to say who did which half.

4.1 Authentication

  • scrypt password hashing with a random per-user salt. scrypt is memory-hard, which resists GPU-accelerated cracking in a way plain SHA-256 does not.
  • HMAC-SHA256 signed tokens carrying a version counter, so raising one column invalidates every token already issued for an account — the revocation that stateless tokens normally lack.
  • Constant-time comparison for both passwords and tokens, so response timing does not leak how much of a value was correct.
  • Password reset by one-time code, stored only as a hash, expiring in fifteen minutes, capped at five attempts, and answering identically whether or not the account exists so it cannot be used to discover registered addresses.

4.2 A defect found and fixed

Midway through the project an audit found that every read endpoint was unauthenticated. The login system was sound; it simply was not applied to the routes serving data, because those had been written before authentication existed and used a bare request with no headers. A request with no credentials returned the full patient list, every clinical note, and the slide images. One endpoint also accepted anonymous writes.

Both halves were fixed together — the server now requires a session, and the client attaches its token — and five tests were added so the hole cannot reopen unnoticed.

4.3 Audit trail

An append-only log records sign-ins, case openings, note saves, annotation saves, slide uploads and report sign-offs, with the actor's name and role copied in rather than joined, so an entry still reads correctly years later if that account is renamed or removed.

Routine worklist polling is deliberately not logged. It runs every four seconds per signed-in user and would add roughly 900 rows an hour of noise, burying the entries that matter. Opening one patient's record is logged; listing the queue is not.

The codebase is an npm workspace with four packages: the two front-ends, the API, and a shared library holding the account types and API calls both front-ends need.

5.1 Decisions worth recording

  • Two front-ends, not one. Merging them would make a CHC attendant download the console's 599 KB bundle instead of 176 KB to fill in a form, on exactly the connections least able to afford it. Separate origins also keep the two sessions isolated from one another.
  • A shared package for what genuinely repeated. The account types and calls existed twice and had already drifted — the intake app's role type had never gained physician, so the same string meant different things in different bundles. One definition makes that impossible.
  • The heavy viewer is lazily loaded. OpenSeadragon and Fabric.js are 349 KB and are not fetched until a slide is actually opened.
  • Incremental polling. The worklist sends the newest timestamp it holds and receives only what changed, so an idle queue transfers an empty array rather than every case every four seconds.

6. Engineering practice

PracticeDetail
Type safetyTypeScript in strict mode across all four workspaces; the build fails on a type error.
Testing23 integration tests against a real server and a throwaway database, covering authentication, role permissions, concurrent saves, and incremental polling.
Test-data safetyThe suite derives its own database name and refuses to run if it ever resolves to the same one as the live database.
Referential integrityForeign keys with explicit delete behaviour. Notes cascade with their case; a case survives the deletion of the account that submitted it.
BackupsA database snapshot at startup and daily thereafter, pruned to the newest seven.
ConfigurationEntirely environment variables. The server refuses to start in production without a real signing key rather than falling back to a published one.
Types earning their place. Introducing strict TypeScript surfaced two live defects. Saved clinical notes were never displayed — the text areas read only the unsaved draft, so text reached the server and then became invisible. And a guard checking that an account still existed compared against a pending promise, which is always truthy, so a deleted account would have passed. Both were found by the compiler, not by testing.

8. Limitations and further work

  • Upload is not resumable. A 1.2 GB slide over a 2 Mbps rural connection takes about 85 minutes as a single request; a dropped connection starts over. Chunked, resumable transfer is the highest-value next piece of work.
  • No notifications. Each participant must check the queue. Notably a slide that fails to convert tells nobody, so the uploader may assume it succeeded.
  • Single instance. The rate limiter keeps its counters in memory, so running more than one copy of the API would multiply every limit.
  • Not deployed. The tile service depends on a native library, so it needs a container rather than a serverless host, and slide storage needs a persistent volume that grows by roughly a terabyte per twenty slides a day.
  • Export resolution. The annotated image exports at 4,096 px — about 3% of native width. Exporting the annotated region at full resolution would be more useful diagnostically than the whole slide reduced.

9. Conclusion

The imaging problem is solved: a gigapixel slide opens in a browser in seconds over an ordinary connection, annotations stay anchored to the tissue, and three clinical roles share one record with their responsibilities separated and recorded. The remaining gap is upload rather than viewing — getting the slide to the system is now the slow step, and resumable transfer is what would make the platform dependable on the connections it is designed for.
